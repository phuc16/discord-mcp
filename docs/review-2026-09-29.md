## Fakes tightened

`tests/fakes/fake-discord-port.ts` now validates like Discord: members and bans have the real shape (`user.id`, no top-level `id`, ordered numerically for paging); stickers need a known content type, matching filename and base64 (upload field recorded as `file`); threads check name, archive duration, parent type and one thread per message; forum posts need a forum channel, content and known tags; roles validate name, permissions and colour and protect `@everyone`; automod checks the event/trigger pairing and action metadata; bulk ban with nobody bannable errors; ban seconds are bounded; a channel parent must be in the same guild. `FakeGatewayClient` models partials, `shardReady`, `shardResume` and `shardDisconnect` the way discord.js emits them.

## Known limitations

- Dynamic client registration is still open. The redirect policy (https or loopback by default, or `http.allowed_redirect_uris`) and `http.max_clients` bound it; deployments that need more should restrict `/register` at the network layer.
- `OPTIONS /mcp` returns 401 because the bearer middleware runs first, so browser-based cross-origin MCP clients cannot call `/mcp`.
- With `safety.allow_token_confirm: true` a confirmation token is a bearer secret bound to tool, input and principal, not to a human. The default is elicitation only. Clients without MCP elicitation cannot run destructive tools unless the operator opts in.
- Rule owner permissions are cached for 60 s, so a demotion that arrives without a gateway event stops rules up to 60 s late. Session permissions rely on gateway events and the refresh-on-token path, not on periodic polling.
- All regex conditions share one worker and a serial queue with a 100 ms kill timeout. A pathological pattern fails closed (no match) but costs each event up to 100 ms and a worker respawn, so a hostile rule owner can slow other rules' `matches` conditions.
- The hierarchy and permission-grant guards apply to `user` principals only. `stdio` and `service` principals act with the bot's own authority; the fake does not model the bot's own role position, so the bot-hierarchy failures Discord returns are covered only by the port unit tests.
- A rule skips message events authored by any bot (`author_is_bot`), not only its own bot, so bot-to-bot workflows cannot be built with message rules.
- The fakes cannot see the multipart field name on the wire; that assertion lives in `tests/unit/discord/port-misc.test.ts` at the REST layer.
- The refresh grace test waits 10.5 s of real time because the auth provider captures `Date.now` when it is built and cannot be driven by fake timers.
- The stdio lifecycle test emits `end` on `process.stdin`; the SIGHUP handler in `startServer` has no test at all. The `.env` startup test builds the CLI into `node_modules/.cache/discord-mcp-qa-dist`.
- `src/server` is at 92% lines, the lowest module; the uncovered lines are process-level branches in `startServer`.
